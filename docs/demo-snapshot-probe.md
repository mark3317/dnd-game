# Рост снимка при боевой истории

16.11.2026. [Исходный замер до runtime-проекции](evidence/snapshot-serialization-probe-20261116.json).
Задача общетехническая: объём сериализации, без новых игровых правил или истории.

## Воспроизводимый stress fixture

Opt-in `SnapshotSerializationProbeTest` берёт шесть бойцов — четыре готовых героя
и двух противников. Одна атака выполняется обычным `CombatDemo.execute` в явно
синтетической близкой расстановке; её ATTACK/DiceEvent-форма повторяется с
уникальным logIndex20/100/500 раз. Журнал содержит максимум последние200 записей,
по одному событию и броскам на запись: это намеренно плотная stress history.

Это **не**20/100/500 реально сыгранных действий, оценка баланса, длительности
боя или размер типичной партии. Фикстура проверяет сериализуемую форму данных.
Для каждого размера сравнивались исходный полный battle history, удаление
дублирующих battle.events/diceEvents с сохранением всего log и дополнительная
экспериментальная обрезка log до200.

Измерены UTF-8 байты `ServerMessage.Snapshot(RoomView)` и время encode/decode
GameWireJson в JVM:10 прогревов, затем50 измерений каждой операции на вариант.
Каждый вариант проходит точный round-trip; текущие механические поля, последние
200 journal entries и их PresentedRoll IDs сравниваются без изменений.
Не измерены TCP, сжатие/заголовки websocket, UI, внешняя модель, GPU/TTS или звук.
JIT/GC и порядок вариантов не изолированы, поэтому времена одного прогона
не являются строгим доказательством ускорения всех клиентов.

## Выбранное минимальное изменение

После рассмотрения этих чисел основной агент согласовал проекцию только
выходящего снимка. `AdventureState.publicRoomSnapshot()` оставляет journal
takeLast200 и весь battle.log, но делает публичные combat.events/diceEvents
пустыми. `Rooms.Room.publish` вызывает этот helper; room.adventure, его полные
histories, обработка действий, бросков и journal остаются каноническими.

Первичные авторитетные события воспроизведения — `journal[*].combatEvents` /
`diceEvents`, их ID `${entry.id}:combat:${index}` не меняются. При reconnect
клиент получает те же200 journal entries и текущий механический снимок;
исторический baseline не должен проигрываться заново. Новый подтверждённый
event продолжает поступать через journal. Приватные токены не добавляются.

Для сетевого `CombatPrototypeScreen` полная event queue из battle.events уже
не использовалась, но events.size закрывал окна лога/помощи. Клиентское направление
переводит этот курсор на сохранённый полный battle.log.size и создаёт локальную
event queue только для учебного боя. Полный log сохраняется, поэтому не теряется
UI-эквивалент истории и не требуется новое поле/версия протокола.
Это существующий монотонный курсор в пределах боя; новый бой создаёт новую
сцену/инициативу. Для будущей обрезки log понадобится отдельный абсолютный
курсор и решение об исторической доступности — сейчас это не реализуется.

Новые `RoomSnapshotProjectionTest` проверяют сохранность канонических histories,
пустые public battle arrays, неизменный полный log, новое событие GUARD в journal,
отсутствие повторного броска при resume, реальные KMP/TCP клиенты и стабильные
event IDs после reconnect. Probe actual-проекции вызывает тот же runtime helper,
а не собственную замену. Эти изменения подготовлены после исходного замера;
их общий compile/test и повторный actual-helper probe ещё ожидаются у интегратора.

## Команда

```text
DND_RUN_SNAPSHOT_SERIALIZATION_PROBE=1 ./gradlew :server:test --tests ru.markn.dnd.server.SnapshotSerializationProbeTest --rerun-tasks --console=plain
```

Без флага тест пропускается JUnit assumption. Текущий результат пишется в
`server/build/reports/snapshot-serialization-probe.json`; frozen evidence выше
не перезаписывается. Report хранит source/harness SHA-256, raw timings и ограничения.
API/TTS-запросов0, оставшийся бюджет135 не менялся.
