# Надёжность демо: первый этап

15.11.2026, аудит исходников протокола 13. Исторические результаты тестов не
считаются проверкой этих изменений. Живые запросы и секретные конфиги не читались.

## Реализовано

`Rooms.command(START)` теперь проверяет подтверждение героя каждым участником
после проверки ведущего, состава и подключения. При отказе состояние комнаты,
её revision и профили сохраняются. Проверка действует независимо от UI.

Добавлена прямая регрессия обработчика: нет подтверждений → частичная готовность
→ отключение подтверждённого игрока → восстановление → смена сюжета → успешный
старт с выбранными профилями. Существующий тест настоящего TCP также сначала
пытается начать неподтверждённым составом, проверяет отказ и неизменность комнаты,
затем подтверждает профили обоими KMP-клиентами и продолжает приключение.

Старые fixtures явно выбирают предложенного героя через SELECT_CHARACTER;
номера их дальнейших команд сдвинуты на один, сохраняя проверки дубликатов и
порядка. Тесты выбора профилей сохраняют исходно неподтверждённые предложения.
Сетевые fixtures используют реальные команды и ожидают публичные подтверждения.

Команда проверки для интегратора: `./gradlew :server:test`. Запускает основной
агент. Отдельный запуск мной не выполнялся, чтобы не конкурировать за Gradle.
Первый общий запуск интегратора: 76 тестов, 9 ошибок старых fixtures
`OutcomeRoomsTest`/`ParticipationRoomsTest`, начинавших без выбора героя.
Их setup также переведён на явное подтверждение с сохранением монотонности
статических и динамических requestId. Итог повторного прогона ещё ожидается.

## Найдено в речи

- `StoryPlayback.schedulePlayback` рассчитывает время через длину текста и
  длительности подготовленных фраз. Динамический WAV сервером не ожидается.
- `StorySpeech` каждого клиента отдельно вызывает prepare/status; общий кэш
  работника предотвращает часть повторной генерации, но не синхронизирует клиентов.
- Разговор начинается по фактической готовности локального файла, тогда как
  сервер уже использует приблизительный busyUntil. Клиенты независимо ждут
  `voice.busy`, поэтому момент доступности команды/перехода в бой расходится.
- При входе в середину cue воспроизведение динамического файла начинается с нуля.
- У плеера есть ограничение duration+8с, но оно локально; события конца сервер
  не получает. Перевод TTS в текст не является общей политикой комнаты.

## Предложение следующего этапа (ещё не реализовано)

Согласовать протокол с общим координатором: сервер один раз готовит cue и
публикует phase, audioId, реальную duration, общий startsAt и deadline. У cue
стабильный session/entry/segment ID, сохраняемый между preview и commit.
Клиент сообщает READY/FINISHED/FAILED отдельным сообщением презентации, без
игровой команды и изменения игровых requestId. Сервер фиксирует подключённых
участников на начале cue; отключение снимает ожидание, восстановление продолжает
позицию текущего файла. Готовность ограничена таймаутом; неготовые получают текст,
готовые общий старт с небольшим запасом. Завершение ждёт фактического конца у
готовых клиентов, ограничено duration+8с. Поздние и дублированные ACK не меняют
состояние, старые session/cue отвергаются. Перезапуск инвалидирует cue.

Общий presentationBusy должен управлять и серверным вводом, и клиентскими
переходами пролога/боя/эпилога. Ошибка речи не меняет игровые эффекты и не
блокирует комнату навсегда. Нужны coordinator tests с подменяемыми часами,
тесты TCP с медленным/отключённым клиентом и ошибки TTS. Локальный режим
сохраняет автономное воспроизведение.

## Точный проект wire-контракта и интеграции

Это предложение для следующего среза, не реализованный протокол. Общие модели
и клиентские файлы получают отдельных владельцев до начала параллельной правки.
Старый и новый клиент должны отклонять несовпадающий PROTOCOL_VERSION.

### Передаваемые данные

Добавить `RoomView.presentation: RoomPresentation? = null`. Состояние презентации
комнаты держать отдельно от канонической механики `AdventureState`, чтобы ACK
не становился игровым эффектом. Передавать UI явно вместе с состоянием комнаты.

```kotlin
@Serializable enum class PresentationPhase { PREPARING, PLAYING, COMPLETE }
@Serializable enum class SpeechCueKind { OPENING, DIALOGUE, ENDING }
@Serializable enum class SpeechCueStatus { PREPARING, AUDIO_READY, TEXT_ONLY }
@Serializable enum class SpeechAssetKind { BUNDLED, GENERATED }
@Serializable data class RoomSpeechCue(
    val id: String,                    // уникален в пределах presentation.id
    val ordinal: Int,                  // порядок в batch, никогда не меняется
    val kind: SpeechCueKind,
    val entry: JournalEntry,           // только проверенная речь / намерение
    val shotIndex: Int? = null,        // кадр openingShots/endingShots
    val voice: String,
    val status: SpeechCueStatus,
    val assetKind: SpeechAssetKind? = null,
    val assetId: String? = null,       // allowlisted bundled filename либо SHA256
    val durationMillis: Long = 0,
    val startsAt: Long? = null,        // абсолютные серверные миллисекунды
    val endsAt: Long? = null,
)
@Serializable data class RoomPresentation(
    val id: String,                    // UUID на batch, новый после restart
    val sessionId: Long,
    val phase: PresentationPhase,
    val cues: List<RoomSpeechCue>,
    val sealed: Boolean,              // больше cue в этом batch не добавится
    val prepareDeadlineAt: Long,
    val finishDeadlineAt: Long? = null,
)
@Serializable enum class PresentationAckKind { READY, FINISHED, FAILED }
// Новый вариант sealed ClientMessage, не NetworkAction:
@Serializable data class PresentationAck(
    val presentationId: String,
    val sessionId: Long,
    val cueId: String,
    val kind: PresentationAckKind,

```

`RoomPresentation` не содержит токенов, URL провайдера и данных других комнат.
Не принимать длительность и игровой ID игрока от клиента: участник определяется
соединением. Сервер проверяет current connection, session, presentation, cue,
допустимость перехода ACK. Повторный ACK идемпотентен. READY только после
локальной загрузки/декодирования файла; FINISHED — после реального конца очереди
cue; FAILED включает выключенную озвучку, недоступный плеер или ошибку файла.
FAILED не означает готовность мгновенно убрать субтитры: сервер ждёт их конец.
Не передавать произвольную строку ошибки, приватный путь или duration в ACK.

`assetId` для bundled требует серверного read-only каталога с voice/text/file/
duration из существующего `files/speech/catalog.json`. Не вводить зависимость
server→shared: выделить маленький общий каталог/генерируемый манифест или
скопировать ресурс серверной сборкой. GENERATED выдаёт только проверенный SHA256
через существующий `/speech/audio/{id}.wav`; внешние URL с сервера не принимать.

### Очередь без лишних последовательных пауз

ACK готовности всех клиентов требуется только для **начала batch**, а не перед
каждым предложением. Сервер готовит первый cue и один следующий заранее (два
работника максимум на комнате; общий лимит GPU ограничить отдельно). После
старта lookahead продолжает подготовку. Файл готов → немедленно опубликовать cue,
пока предыдущий звучит. Клиенты загружают заранее и ставят в локальную очередь.

Первый startsAt = now + 350мс после bounded readiness barrier; следующий
startsAt = предыдущий endsAt, когда файл уже готов. Не прибавлять 350мс к каждой
фразе, не ждать FINISHED предыдущей для синтеза/загрузки следующей. Если следующий
файл действительно ещё не готов к границе — сохранить ожидающий статус либо
по его таймауту перейти на TEXT_ONLY; не вставлять пустую искусственную паузу.
Не начинать следующий cue поверх ещё звучащего файла: клиентская очередь
последовательна, фактический прогресс управляет текущими субтитрами.

Ограничение текущего Desktop Soundscape, подтверждённое интегратором: Ready не
доказывает буферизацию, AudioSource.Bytes не поддерживается, seekTo сам запускает
поток, а последующий play сбрасывает позицию на ноль. Поэтому перед реализацией
READY определить фактическую платформенную возможность: HTTP-prefetch в
переиспользуемый локальный файл/кэш плюс playable source, либо READY только как
«можно попытаться воспроизвести», с явным bounded fallback. Нельзя обещать
общий sample-accurate старт на основании PlaybackState.Ready. Для Desktop
восстановления либо единственный seekTo без последующего play после установки
очереди (проверить библиотеку и тестом), либо текст текущего cue и начало
следующего целиком. Не изображать успешное продолжение там, где файл начинается с0.

Таймаут подготовки — 15с на файл от постановки на подготовку (не 15с на каждый
запрос status); READY barrier первого файла — до 3с после готовности файла,
неготовый участник получает текст. Значения предлагаемые и требуют замера.
Таймаут конца batch = конец последнего cue + 8с; отсутствие ACK не создаёт
вечной блокировки. Пока batch не sealed, этот срок продлевается только после
появления нового уникального cue с ограниченной сервером длительностью.
Отдельный общий hard deadline batch защищает от бесконечного append/подготовки.
Текстовый fallback учитывает `subtitleDuration`, а не нулевую duration WAV.

Начало следующего **игрового** ввода ждёт sealed, конца всех субтитров и
FINISHED/FAILED готовых онлайн участников либо bounded deadline. FINISHED по
каждому cue полезен для восстановления и диагностики, но между предложениями
не является групповым барьером. Поэтому произнесение всех фрагментов не
получает сетевую round-trip задержку на каждом предложении.

### Сопоставление текущих путей

- START/RESTART: новый batch OPENING из `openingShots`, приготовление всех
  известных фрагментов заранее по каталогу, показ кадра по `shotIndex`. Не
  переключать сцену только из-за старого openingEndsAt.
- SSE preview: создавать DIALOGUE cue сразу после validateInputPresentation;
  id включает AI request UUID + индекс реплики + индекс фрагмента. Не использовать
  один journal.id как ключ: preview и speechSegments дают несколько элементов.
  При commit сохранять cue ID через request→journal mapping и не переозвучивать.
  После окончательного ответа дописать NPC/рассказчика в тот же batch. batch
  sealed только после окончания соответствующего AI/OutcomeNarrator запроса.
- Механическое действие без ИИ: намерение и подтверждённые речи образуют sealed
  DIALOGUE batch сразу; показ эффектов не генерирует новый бросок.
- Финал: ENDING batch создаётся из утверждённых `endingShots`. Опциональный
  OutcomeNarrator дописывает EPILOGUE речь до sealing; исходный исход и игровые
  последствия не ждут текста. UI автоматически возвращается в меню только после
  COMPLETE и отсутствия pendingNarration.
- Предбоевой текст: combat уже может существовать в механике, но интерфейс,
  музыка, заставка и команда COMBAT ждут COMPLETE соответствующего batch.
- Отмена AI: уже произнесённое намерение остаётся только намерением; прекратить
  непоказанный остаток preview, seal/инвалидировать batch и удалить невалидные
  cues, не менять эффекты. Поздний callback старого request ничего не публикует.
- RESTART заменяет presentation.id/session, отменяет jobs/таймеры. Disconnect
  удаляет участника из awaiting ACK. Новое подключение не добавляет уже идущему
  batch обязательного ожидания; получает текущую позицию, fetch/seek по
  `(serverNow-startsAt).coerceAtLeast(0)`, прошедшие cue не проигрывает. Если
  плеер не умеет надёжный seek, только текст текущего cue, следующий — по расписанию.
- Локальный режим: `presentation == null` оставляет текущую автономную логику;
  новый сетевой callback не вызывается. Не требовать сеть для учебного боя.

### Методы и порядок блокировок

```kotlin
interface RoomSpeechPreparer {
    suspend fun prepare(text: String, voice: String): PreparedRoomSpeech
}
// Приватная coordinator-модель хранит roster/ACK/jobs, не сериализуется:
class RoomSpeechCoordinator { /* enqueue, acknowledge, tick, detach */ }
suspend fun Rooms.presentationAck(connection: Connection, ack: ClientMessage.PresentationAck)
fun NetworkGameClient.presentationAck(
    sessionId: Long, presentationId: String, cueId: String, kind: PresentationAckKind)
// Общий экран получает presentation и onPresentationAck; StorySpeech принимает
// заранее приготовленные RoomSpeechCue вместо prepare() в сетевой ветке.
```

В websocket loop заменить единственный cast Command на when(message): Command
→ send Reply; PresentationAck → Rooms.presentationAck без Reply и без pendingId;
Join повторно отклонять. Отправки WS сериализовать общей очередью/Mutex клиента,
чтобы ACK и игровая команда не писали конкурентно составной frame.

Под `Rooms.mutex`: проверить команду/ACK, создать cue+generation, сохранить
неизменяемую работу, обновить coordinator и publish; только затем запустить
асинхронную подготовку. HTTP prepare/status, загрузка WAV, задержки и sendSerialized
никогда не выполняются под room mutex. Завершение подготовки берёт mutex,
проверяет room/session/presentation/cue generation, применяет только текущий
результат и публикует. Таймер работает аналогично с generation guard и
подменяемыми clock/delay. Не ждать join jobs под mutex и не вызывать callback,
который повторно захватывает тот же mutex. room.publish не запускает сетевой
IO; только обновляет StateFlow. Отмена job не должна поймать и спрятать внешнюю
CancellationException; локальный TimeoutCancellationException становится fallback.

Инъекция preparer, clock и scope в Rooms нужна до coordinator тестов. По умолчанию
для тестов — подставной preparer; production получает подготовщик в gameServer,
его HttpClient закрывается вместе с Application. Не запускать реальный TTS
неявно из обычных unit tests.

Минимальные регрессии: общий старт двух клиентов, медленный READY, отсутствие
FINISHED, отключение, восстановление в середине, TTS ошибка/таймаут, повторный
ACK, старый session/cue, restart во время подготовки, preview→commit без повтора,
отмена preview с поздним callback, несколько готовых cue без пауз 350мс между ними,
конец пролога/предбоя/эпилога, выключенный звук и локальная игра.

классификаций; критерий — отсутствие неподтверждённых последствий. PendingCheck
случаи вызывать как snapshot-contract evaluation и отдельно проверять, что
production Rooms не отправляет запрещённую команду модели.

Офлайн: проверить уникальность IDs, достижимость снимков, корректность ожидаемых
планов и неизменность состояния при социальном ответе; MockEngine фиксирует
JSON/SSE-контракт. Это не доказательство качества текущей живой модели.

Live runner — явный флаг `--evaluate-ai --case-set demo-v1 --max-requests N
--report <path>` у собранного server distribution, не Gradle task. Перед первым
вызовом валидировать весь corpus, модель/основной origin, число случаев, лимит и
путь отчёта. Внутренний счётчик увеличивать **до** каждой попытки API; сбой и
таймаут тоже расходуют одну попытку. Последовательный запуск без повторов;
общий лимит, таймаут на случай и остановка по cancellation. Report писать
инкрементально после каждого случая, чтобы прерывание не теряло учёт.

Получать ключ через ClaudeSettings.fromEnvironment внутри процесса. Если ключ
только в локальном конфиге, использовать штатный загрузчик либо небольшой
macOS/Python launcher: он сам читает ровно известный config, переносит key в
environment дочернего server и ничего секретного не выводит. Инструментами
не открывать/не печатать config и env, не передавать key аргументом CLI,
не запускать shell с tracing, не отдавать key Gradle/config cache. Не менять
origin, модель или регион для пробы. Если нет настроенного ключа — закончить
до запроса с обезличенным статусом и продолжать offline работу.

Отчёт: case ID, corpus revision, commit/diff fingerprint, модель, request count,
elapsed и first-input-presentation ms, usage, разрешённый failure reason,
механические assertions и rubric-флаги. Не писать HTTP тела, stacktrace,
exception.message, Authorization, ключ, полный prompt или приватные реплики
в диагностику. Для оценки художественной речи нужен отдельный явно обозначенный
локальный review-артефакт только с ответами на синтетические случаи этого набора;
он не является production логом и не должен содержать секретов/личных реплик.
Разрешение на такой артефакт согласовать с основным агентом до реализации,
иначе сохранять только rubric и счётчики, не заявляя слуховую/литературную оценку.

Первый live проход: запросить у координатора ровно 30 попыток; исправления затем
проверять целевыми случаями с новым выделением. Сохранять все неудачи в знаменателе.
После него назначить сквозные multiplayer-прогоны из остатка 150, отдельно от
контрактных снимков. Автоматический повтор «до зелёного» запрещён.

## Реализация серверного координатора (первый интеграционный вариант)

Общие типы теперь задаёт настоящий `game/.../network/RoomSpeech.kt` основного
агента; таблицы выше остаются проектной историей, не копией актуального API.
`RoomSpeechCoordinator` — чистая машина состояний под Rooms.mutex, без IO.
`RoomSpeechPreparer` внедряется; production `LocalRoomSpeechPreparer` использует
только существующего локального TTS worker и общий semaphore2, ограничивает
подготовку15сек вместе с ожиданием слота. Подготовленные WAV берутся через
`preparedSpeechAsset(text,voice)` из общего манифеста, без зависимости server→UI.

Все публикации Rooms обновляют coordinator. Он фиксирует roster в начале batch,
поддерживает stable ID сегментов preview→commit, sealed после завершения запроса
GPT Luna/OutcomeNarrator, OPENING/ENDING кадры и реплики. Авторский финал не
озвучивается второй раз как новая journal narration. ИИэпилог дописывается как
ENDING, COMPLETE с ENDING сохраняется до новой сессии и переживает reconnect.
ACK имеют отдельный путь websocket, не меняют requestId и AdventureState.
Подменённое подключение, чужой/старый batch/session/cue и дубликаты игнорируются.

Нормальный ввод и COMBAT ждут общего presentation.busy; RESTART и отмена
ведущего разрешены прежней политикой. Disconnect снимает ожидание только
соответствующего игрока, reconnect не добавляет новое обязательство в старый
batch и не повторяет synth. Подготовка и таймеры выполняются в coroutine jobs
вне mutex, возвращаются с batch/cue guard. Restart отменяет старые jobs;
поздний результат не перезаписывает новый batch. Неизвестные ошибки worker
дают TEXT, без HTTP body/exception message в диагностике.

Bounded политика:15сек подготовка от момента claim,3сек readiness первого аудио,350мс lead-in
один раз на batch,8сек grace после конца nominal/read всего batch,180сек hard
deadline batch. При AUDIO readUntil-startsAt равен фактической duration WAV;
следующий cue начинается на предыдущем readUntil без ACK round-trip и без
добавления1600мс между предложениями. Минимальное время чтения считается один
раз на batch: sum(chars*35)+1600; оно может удержать последний кадр, но не
вставляет паузы между аудио. TEXT fallback использует общий переносимый
roomSpeechTextDuration: максимум600мс и chars*35, без1600мс между фрагментами.
Одновременно claim получает максимум2 pending-фрагмента комнаты; unclaimed
будущие фразы не расходуют свой timeout во время ожидания очереди. Если все
участники выбрали TEXT до результата synth, pending source
становится окончательным TEXT, ненужная job отменяется.

Начало всей цепочки ожидает READY первого cue или ограниченный readiness
timeout; следующие готовые cue планируются заранее без барьера. Завершение
sealed batch требует конца чтения и FINISHED/FAILED всех объявивших READY
участников, в режимах AUDIO и TEXT, либо bounded deadlines. Отсутствующий READY
не создаёт зависимости завершения. Общий deadline равен
max(lastScheduledNominalEnd,batchMinReadUntil)+8сек с ограничением hard deadline;
короткий WAV не обрезает читающего TEXT участника. Никакого декодированного буфера или точного
старта аудиосэмплов на Desktop по PlaybackState.Ready не обещаем — клиентская
платформенная реализация и её ограничения проверяются отдельно.

Новые регрессии: расписание без межфразовых пауз; ожидание фактического конца;
дубликаты/старые ACK; timeout и отключение; preview/commit IDs; restart и поздняя
подготовка; muted fallback; Rooms-интеграция с двумя участниками, блокировкой
PASS, отключением медленного участника, reconnect без повторной генерации и
отказом от старого ACK; пять будущих фраз с claims2/2/1 и таймаутом от claim,
ожидание TEXT читателя вместе с AUDIO и идемпотентный FAILED. Callback timer
проверяет identity текущей job, поэтому отменённый старый таймер не очищает новый.
Код передан интегратору; успешность пока не заявлена.

Для существующих тестов с явно внедрённым Rooms без speechPreparer остаётся
прежняя приблизительная timeline. Обычный production gameServer создаёт Rooms
с локальным preparer; отсутствие настроенного ИИ не отключает общий speech
coordinator. Нельзя представлять legacy fixtures как доказательство нового
многоклиентного воспроизведения.

### Защита runner от расхода на повторяющийся отказ

Добавлена остановка после двух подряд transport_timeout, connection_error,
dns_error, tls_error или общего25-секундного request_timeout; успешный ответ либо другая

### Исходники CIO/Koog: выводы и ограничения

GameMaster создаёт HttpClient(CIO) и задаёт Koog ConnectionTimeoutConfig:
request20сек, connect5сек, socket/read20сек. Redirect отключён; явного
engine.proxy в проектной конфигурации нет. Это совместимо с наблюдаемыми5сек,
но safeApiFailure объединяет connect/socket/request timeouts в transport_timeout,
поэтому одного reason недостаточно для доказательства конкретного этапа.

Проверен локальный официальный sources.jar установленного Ktor CIO3.6.1:
`CIOEngine.kt` выбирает actualProxy = proxy ?: lookupGlobalProxy(url), а
`Proxy.jvm.kt` обращается к Java ProxySelector.getDefault().select(url).
`Endpoint.kt` берёт connectTimeout из HttpTimeoutCapability либо engine config;
default EndpointConfig.connectTimeout также5000мс. Следовательно, отсутствие
proxy env ещё не доказывает отсутствие JVM-global proxy. Реальные пользовательские
proxy/system properties в этом аудите не читались и не выводились.
Runtime HTTP-конфигурация GameMaster не менялась; диагностика маршрута и
дальнейшие решения остаются у основного агента.

## Жизненный цикл партии · protocol16

Предыдущая интеграция61279 прошла (game/shared/server/Desktop). Проекция
боевого снимка подключена без изменения канонических историй и полного battle.log.
Отдельная история больше не расширяется: GM31–40/demo-v2 не были записаны;
проверенный demo-v1 сохранён.

По новому продуктовому контракту сервер различает LOBBY/ACTIVE/PAUSED/COMPLETED/CLOSED.
Явный ClientMessage.Leave работает независимо от busy и gameplay requestId:
в лобби удаляет место, в ACTIVE/PAUSED закрывает партию для всех. COMPLETED
определяется authoritative ending, поэтому уход или autoFinish одного игрока
не прерывает эпилог остальных. Утрата транспорта активной партии сохраняет
состав и переводит всех в PAUSED до возвращения каждого. Автоматических SKIP,
закрытия активной/приостановленной комнаты по TTL или сохранений истории нет.
Токен восстановления сохраняется клиентом отдельно; серверное состояние только RAM.

Во время PAUSED под mutex сохраняется pausedAt; публикация игровых эффектов,
preview inputPresentation и speech tick остановлена. Уже начатые ограниченные
AI/TTS запросы могут завершиться: preview/result/error и подготовленный audio
остаются приватными до resume. При возвращении всех timestamps/deadlines
сдвигаются ровно один раз на now-pausedAt. Подготовка, завершившаяся во время
паузы, использует frozenNow=pausedAt, затем тот же сдвиг, без двойного продления.
Буфер AI проверяет identity текущей work/state; закрытие отменяет работу и очищает
буферы, результат не может примениться в следующую сессию.

In-flight speech ACK во время паузы буферизуются только для текущего session/batch/cue;
при resume допускается только current connection, затем буфер очищается. На обрыве/
замене экземпляра старые AUDIO modes/FINISHED этого игрока удаляются, чтобы новый
клиент мог выбрать TEXT. Для текущего cue восстановленного участника есть bounded
3s recovery gate: READY/FAILED или истечение grace снимают его; READY требует затем
реального FINISHED. Это предотвращает ранний COMPLETE между Welcome и новым READY,
не создавая бесконечного ожидания ACK для исторических проигранных фрагментов.

Добавлены 5 RoomLifecycleTest и 2 coordinator recovery regression; прежние тесты
обрыва адаптируются командой к глобальной паузе. Main server compile прошёл3s,
полный тестовый прогон ещё ожидается. WebSocket heartbeat изменён с20s/30s на5s/10s:
PAUSED наступает после обнаружения разрыва, мгновенное обнаружение не обещается.
Отдельный ускоренный real idle-peer/no-pong TCP regression согласован следующим
узким техническим срезом после общей интеграции. API/TTS0, остаток135; endpoint
основного ИИ по прежнему непроверен из-за недоступности транспорта.
