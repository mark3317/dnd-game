# AGENTS.md

## Назначение и контекст

Этот файл содержит постоянный контекст и правила для агентов, работающих с репозиторием `dnd-game`. Читай его при начале новой сессии вместе с `README.md` и конфигурацией затрагиваемых модулей. Актуальное состояние реализации проверяй по исходникам и Git diff.

Обновляй этот файл, когда пользователь принимает значимые решения о продукте, архитектуре или процессе работы. Сохраняй причины важных решений кратко; не превращай файл в журнал переписки. Пользовательские указания текущей сессии имеют приоритет.

## Актуальный срез реализации · 16.11.2026

Пользователь завершил текущий цикл разработки: закончить уже начатые правки и
проверки, зафиксировать актуальную играбельную версию коммитом и push, затем
остановиться. Новые улучшения и расширения не начинать без нового поручения.
Полная исходная цель презентационного демо не означает подтверждённую приёмку.
Итоговый срез протокола 16: `docs/demo-checkpoint-protocol16.md`, 370 JVM и
12 Python-тестов прошли, сборки Desktop/Android/Web/server готовы, iOS shared
скомпилирован. Ручная приёмка и живой проход GPT Luna не подтверждены.

Новое согласованное правило сетевой партии: сохранений истории нет. Явный,
подтверждённый выход любого игрока завершает текущую партию для всех. Обрыв связи,
вылет или закрытие приложения без подтверждения не считаются выходом: остальные
ждут этого игрока на общей паузе, он может восстановить участие, в том числе после
перезапуска клиента. Поэтому прежние пропуск отключённого/продолжение без него и
хранение токена только в памяти больше не соответствуют целевому поведению.
Контракт реализован в протоколе 16: временные данные восстановления
соединения не являются сохранением истории; каноническая партия остаётся на
живом сервере. Не выдавать прежние тесты переподключения за проверку новых правил.

Текущий приоритет пользователя: доработки отдельной истории пока отложить,
заниматься оставшимися техническими и дизайнерскими вопросами самой игры.
Не расширять сюжетные ветки/действия до нового указания; уже проверенную
реализацию сохранять. Общие переходы, синхронизация речи, UI, задержки и
устойчивость остаются в работе; текущий статус — `docs/demo-progress.md`.

## Преемственность генерации медиа

Любая новая генерация или перегенерация медиа должна учитывать уже созданные
материалы проекта: аватары, окружения, иллюстрации, анимации, голоса, музыку и звуки.
Перед запросом найди и просмотри/прослушай подходящие существующие материалы,
выбери актуальные эталоны и используй их как референсы. Для изображений передавай
сами изображения; для других медиа используй доступные провайдеру образцы,
идентификаторы голосов, параметры и описание подачи. Сохраняй узнаваемость персонажей,
единый художественный/звуковой стиль и непрерывность сцены. После генерации сравни
результат с эталонами и исправь расхождения до подключения. Записывай использованные
референсы и промпты рядом с материалами. Устаревшие или отклонённые варианты не
подменяют актуальные эталоны. Изменение общего стиля требует явного указания пользователя.

## Концепция игры: согласованное направление
15.11.2026 переход к бою ожидает полного завершения предбоевого описания рассказчика:
до конца субтитров и фактической озвучки остаётся разговорная сцена с подготовленным
фоном текущей локации и аватарами. Затем включаются боевая музыка, заставка,
инициатива и экран боя; команды во время ожидания заблокированы.

15.11.2026 по запросу на общую чистку интерфейса настройки звука и отображения
объединены: раздельные выключатели и громкость музыки/озвучки, размер субтитров
80–140% с предпросмотром, движение камеры. Параметры сохраняются локально и доступны
из меню, подготовки группы, меню приключения и боя; озвучка использует общее состояние
настроек. Убраны отдельные окна музыки/речи, перекрывавшая панель кнопка озвучки,
недоступные элементы генерации из подготовки и редактора. Тестовый режим «Телефон»
оставлен только в учебном бою. Визуальную оценку по-прежнему выполняет пользователь.

15.11.2026 уточнён конвейер разговора: ведущий в том же запросе первым выдаёт
`inputPresentation` — реплики героя (SPEECH, прямая речь) и описания его намерений
рассказчиком (ACTION, третье лицо с именем героя). Смешанный ввод разделяется по порядку.
Сервер проверяет законченный блок из SSE и сразу публикует его для TTS, пока остальной
ответ ещё генерируется; отдельного запроса классификации нет. Исходный ввод хранится
в журнале с `speechEligible=false` и напрямую не озвучивается. До проверки плана это
только намерение без игровых последствий; успех не объявляется заранее. Готовые кнопки
получают описание рассказчика без запроса к модели. Новые длинные ответы делятся на последовательные
фрагменты, следующие голоса готовятся в фоне; готовые записи сохраняют свои границы.
Не повторять фразу игрока после ответа модели. Субтитры озвучиваемого разговора
раскрываются вместе со звуком, при сбое голоса остаётся последовательный текст.
Пак рассказчика для маскировки пауз пока предложен, не подключён: одна короткая
уместная вставка, без выдуманных мыслей NPC или неподтверждённых последствий;
резкие и неоднозначные действия требуют отдельной политики. Детали и ограничения —
в `docs/media-implementation-plan.md`, раздел о задержках разговора. Протокол 13.

15.11.2026 добавлена заставка «Бой начинается»: плавное появление надписи, затем
свой бросок инициативы и раскрытие очереди. Общий экран кубика полупрозрачен,
с затемнением текущей сцены. Вход/выход боевых вставок, раскрытие результатов,
смена поз и переход между приключением и картой анимируются; ввод остаётся
заблокированным до завершения выхода последней вставки. Броски берутся из
подтверждённых событий и не выполняются повторно ради анимации.

15.11.2026 уточнена подсветка боевой карты: доступные клетки и выделение активного
героя показываются только в свой ход; чужие герои и враги при своих ходах не
подсвечиваются, в том числе во время анимации перемещения. Нажатие клетки выбирает
её сразу, повторное быстрое нажатие той же клетки выполняет движение/атаку.

В разговорных сценах ступни аватаров привязаны к нижнему краю сцены без отступа
под субтитры. Имя над головой фигуры появляется только при наведении либо временно
по нажатию (включая телефон); подпись не влияет на положение персонажа.

15.11.2026 по прямому указанию пользователя модель гейммастера переключена на `gpt-6-luna`
через OpenAI-совместимый API прежнего AI STAR с тем же ключом. Локальная настройка и
значения по умолчанию обновлены; прежние имена переменных окружения и файла конфигурации
сохранены для совместимости. Это заменяет прежнее отсутствие решения о смене модели.

Для `gpt-6-luna` сервер задаёт `reasoning_effort=none`: ведущему нужны короткие реплики и
формальные планы, проверяемые движком. HTTP-таймауты Koog заданы явно: запрос/чтение
20 с, подключение 5 с; автоматических повторов нет. Авторизацию OpenAI-ветки добавляет
только Koog (дублирование Authorization давало 401). Схема ответа и проверка игровых
планов сохранены. Две живые проверки через основной AI STAR прошли за 3,7 с (диалог)
и 15,3 с (свободный план); это отдельные замеры, не гарантия задержки провайдера.
`scripts/start-claude-server.ps1 -ProbeCurrent` выполняет ровно два запроса к настроенной
модели; `-ProbeRegion` — два к дополнительному ai.starimg.space и требует отдельного
разрешения на передачу туда ключа. Никакого автоматического перехода на другой регион нет.

15.11.2026 уточнена подача катсцен и реплик: пролог и эпилог проигрываются полностью
для всей группы по серверной временной шкале, без паузы, пропуска и кнопок.
В кадре только иллюстрация и субтитры рассказчика снизу; после эпилога — автоматический
возврат в главное меню. Эти требования заменяют прежний локальный просмотр с управлением.
Все реплики (рассказчик, NPC, игроки) показываются постепенно в едином стиле без плашки;
длинный текст разбивается на последовательные субтитры. Следующий ввод/ход недоступен
до завершения реплик и ожидаемого ответа ведущего. Сервер задаёт времена кадров/реплик,
клиент учитывает смещение часов; переподключение продолжает текущую позицию.
В сцене показывается активный герой и местный NPC, остальные герои скрыты.
Поле ввода появляется и скрывается с анимацией. Музыка меню сменяется музыкой истории
уже при запуске пролога. Протокол 11: сервер и клиенты обновляются вместе.

15.11.2026 уточнены аватары: исходник всегда изображает стоящего персонажа целиком,
от головы до ступней, на настоящем прозрачном фоне. В новельной/разговорной сцене
показывается полноростовая фигура поверх окружения; допустима обрезка границей экрана.
Карточки используют упрощённую портретную обрезку того же исходника, а не отдельный
образ. При каждой новой генерации/перегенерации обязательно просматривать существующие
аватары и передавать их изображения как референсы: эталон рисованного стиля и исходник
внешности конкретного персонажа. Одного текстового описания стиля недостаточно.
Нельзя переносить фон карточки на сцену. Правила и текущие референсы —
`assets/visual/STYLE.md`, полноростовой пак — `assets/visual/standing-v2`.

15.11.2026 уточнён боевой интерфейс: на старте только своя инициатива, затем анимированное появление общей очереди; в локальной группе показывается первый герой. После расхода действия и перемещения ход автоматически заканчивается на сервере. На карте заметно выделяется активное существо и анимируются подтверждённые маршруты всех участников. Взаимодействия — полноэкранные сцены на заранее подготовленном фоне, действующий слева, цель справа, позы/эффекты удара, ранения, уклонения, поддержки и лечения; отдельный боевой кубик скрыт, фактические проверки раскрываются после действия. В ресурсах подключён пак `assets/visual/combat-v1` (2 фона, 6 прозрачных атласов по 6 поз), PNG + Compose-анимация, не GIF. Подробности и будущие покадровые циклы — в `docs/combat-implementation-plan.md`.

На этом раннем этапе новый провайдер/модель ещё не был выбран; последующее прямое решение о gpt-6-luna выше заменяет этот статус.

Мультиплатформенная ролевая игра в стиле DnD, в которой роль гейммастера выполняет нейронная сеть.

Используем упрощённые правила по впечатлению от «Подземелий Чикен Карри». Полная реализация DnD не является целью; шесть характеристик и стартовые правила создания героя согласованы ниже, подробные правила боя ещё не выбраны. Сходство с шоу — ориентир, а не утверждение о его точных механиках.

- Основной формат игры — совместное прохождение с друзьями по сети. Сетевой мультиплеер является согласованной целью проекта.
- Истории рассчитаны на 2–4 игроков; роль гейммастера выполняет ИИ и в это число не входит. Сетевой и локальный режимы поддерживают такой состав.
- В приключении слово у одного игрока за раз, но обязательного кругового порядка нет: гейммастер решает, когда логично продолжить с тем же героем или переключиться на другого. Свободное общение пока идёт репликами текущего игрока в общем поле действий; отдельного чата вне очереди нет. Подробные правила боя определяются отдельно.
- Игра имеет сессионный формат: игроки выбирают отдельные законченные истории с целевой длительностью 40–60 минут. Это ориентир для объёма и темпа приключения, а не жёсткий таймер.
- Помимо самостоятельных историй будут кампании из 3–5 историй: каждая история — отдельная глава одного большого сюжета, рассчитанная на такую же сессию.
- Игроки могут неформально общаться, шутить, импровизировать и предлагать действия, немного выбивающиеся из стилистики мира, по впечатлению от «Подземелий Чикен Карри». Строгий отыгрыш каждой реплики не требуется.
- Гейммастер поддерживает импровизацию и старается вплетать её в происходящее, сохраняя общий сеттинг, причинно-следственные связи и движение сюжета. При отклонениях мягко возвращает внимание к приключению, оставляя игрокам выбор действий. Юмор не отменяет принятые правила и подтверждённые последствия.
- Общее настроение игры — весёлое, увлекательное и вовлекающее: совместное приключение с друзьями, в котором хочется участвовать и узнавать, что будет дальше.
- Игрок может создать собственного персонажа с характеристиками в духе DnD и проходить им разные истории. Персонаж не привязан к одному сюжету; Рин, Мира и Бран остаются готовыми вариантами для быстрого старта. Сценарии должны поддерживать разные составы героев без обязательного присутствия конкретного готового персонажа.
- В редакторе согласованы и реализованы 4 класса (воин, плут, маг-исследователь, бард), 4 расы (человек, эльф, дварф, полурослик), 6 предысторий (солдат, ремесленник, архивист, торговец, моряк, артист) и распределение 15, 14, 13, 12, 10, 8. Бонус характеристики — floor((значение − 10) / 2), здоровье — 12 + бонус телосложения. Специализация класса или предыстории даёт +1 без сложения; подходящий расовый талант даёт +2 один раз за историю по выбору до броска. Максимальный стартовый бонус +5. Рин, Мира и Бран пересобраны по тем же правилам; списки эффектов и параметры в README и Characters.kt. Это наша упрощённая система, не полный DnD.
- В приключении игроки сообщают гейммастеру действия своего персонажа текстом. В бою основные действия выбираются через интерфейс; текстовая импровизация доступна отдельной кнопкой особого действия.
- Для игровых проверок используются броски кубиков.
- Боевая система предполагается пошаговой, в духе DnD; точные правила будут определены позже.
- 15.11.2026 согласован ориентир боевого интерфейса: ощущение понятной упрощённой компьютерной пошаговой игры по примеру Baldur’s Gate 3 и XCOM. Основной цикл — визуальный выбор перемещения, действия и цели с предварительным показом последствий и стоимости; печать ведущему не требуется. Интерфейс адаптируется к большим и маленьким экранам, включая сенсорное управление. Подробный предлагаемый экран и этапы — в `docs/combat-implementation-plan.md`. Конкретные правила, пространственная модель (зоны/клетки), 2D/3D и численный баланс пока не утверждены; предыдущие предложения агента не считать принятыми механиками.
- Отдельная нейросеть или несколько нейросетей будут озвучивать текст игроков и гейммастера.
- Генерация изображений будет визуализировать происходящие события на экране.

15.11.2026 принято направление визуальной подачи: для истории заранее готовится постоянный переиспользуемый пак окружений и NPC; для готовых героев — заранее подготовленные аватары. Для своего героя при создании генерируется набор аватаров с эмоциями, сохраняемый у создавшего героя игрока и используемый в разных историях. Обычная сцена состоит из фона локации и аватаров присутствующих героев/NPC. В особые интересные моменты (сложная проверка, необычное действие, поворот сюжета) отдельная созданная во время игры иллюстрация временно заменяет фон и аватары. Звуки окружения и действий собираем в постоянную библиотеку, сначала из бесплатных источников с правом использования в продаваемой игре. Это направление, не уже реализованный медиа-движок. Детали, предлагаемые этапы и открытые решения — в `docs/media-implementation-plan.md`; стартовые 35 CC0-аудиофайлов и происхождение — в `assets/audio/starter-v1`. Файлы ещё требуют прослушивания/обработки и не подключены к сборкам. Конкретные сервисы медиа, облачное хранение, точные эмоции и лимиты генерации не утверждены.

Это направление разработки, а не перечень уже реализованных возможностей.

Ориентир по подаче изучен по интервью гейммастера Александра Бреганова: [The Flow](https://the-flow.ru/features/podzemelya-chiken-karri-intervyu-s-geym-masterom) и [Sport24](https://sport24.ru/lifestyle/article-670342-my-delayem-shou-i-khotim-chtoby-ono-zhilo-dalshe-a-ne-ubit-yego-aleksandr-breganov-pro-podzemelya-chiken-karri). В них описаны импровизация, свобода неожиданных решений игроков и понятные эмоциональные описания. Конкретный баланс юмора и сохранения сеттинга выше — принятое направление нашей игры, а не точная спецификация шоу.

15.11.2026 дополнено создание аватаров: игрок может загрузить своё фото как образец лица/внешности; аватар сохраняет узнаваемое сходство и выполняется целиком в стилистике игры. Генерация картинки доступна в конце создания персонажа после заполнения характеристик, описания и загрузки фото при его использовании. Фото — необязательный способ задания внешности. Набор эмоций создаётся от принятого стилизованного портрета. Подробный поток и предложения по временной обработке исходного фото описаны в медиа-плане; загрузка/генерация ещё не реализованы.

Первый визуальный пак подготовлен 15.11.2026 в `assets/visual`: 7 фонов/состояний «Затопленного архива», отдельные архивариус и курьер, по 6 выражений Рина (эльф-плут), Миры (дварф, маг-исследовательница) и Брана (человек-воин). Рисованное фэнтези, янтарный свет и прохладные тени — рабочий художественный вариант, ещё не окончательно утверждённый пользователем стиль. PNG, промпты, манифест, предлагаемые привязки к фактам и локальный HTML-просмотр сохранены в паке; интеграции в игру пока нет. В подвале архивариус остаётся за кадром; после спасения грамот сундук пуст, финал затопления скрывает сундук мутной водой. Говорение — отдельная подсветка, не эмоция.

## Поражение и смерть: принято 15.11.2026

Для коротких историй на 40–60 минут согласовано реальное поражение внутри истории без обязательной постоянной потери созданного героя. В общей боевой модели реализованы повязки, одно поднятие за бой и восстановление после победы; в полном демо архива уже подключены перенос ресурсов и финал поражения. Развитие последствий для других историй ещё предстоит.

- При 0 здоровья герой выбывает из боя: не атакует и не перемещается, но ещё жив. Союзник может вернуть его в бой лечебной повязкой по правилам ниже. После победы здоровье каждого выжившего, включая выбывших, становится не меньше 4. Спасбросков от смерти и добивания лежащих в базовой системе нет, чтобы ранняя случайная смерть не оставляла игрока зрителем до конца короткой сессии.
- Поражение столкновения и провал всей истории различаются. Если вся группа выведена из строя и помощи нет, столкновение проиграно. Для значимых столкновений сценарий заранее задаёт последствия: потеря улики или возможности, ухудшение положения, плен, отступление либо финал поражения. Плен/спасение допустимы, если предусмотрены сценарием и укладываются в сессию; ИИ не придумывает обязательное чудесное избавление.
- История может завершиться успехом, частичным успехом или поражением даже при выжившей группе. Финал содержит законченный эпилог с подтверждёнными последствиями решений игроков.
- Гибель — редкий исход явно смертельной ситуации или финала, включая сознательную жертву. Перед необратимым действием игра прямо обозначает риск гибели. Обычный неудачный бросок осмотра или разговора не должен внезапно убивать героя.
- Любой финал сохраняет профиль героя, внешность, аватары, класс и характеристики; следующая самостоятельная история начинается с восстановленным здоровьем. Гибель относится к конкретному прохождению и может сохраняться в его записи; новая самостоятельная история с тем же героем не требует сюжетного воскрешения. Непрерывность смерти в связанной кампании требует отдельного решения. Постоянная смерть профиля не входит в базовую систему; возможный отдельный режим оставлен на будущее.

### Лечение и поднятие: принято 15.11.2026

- Лечебная повязка — расходуемый предмет: восстанавливает 4 здоровья, не выше максимума. Можно лечить себя или союзника; выбывшего лечит только союзник. В бою применение стоит одно основное действие и одну повязку; бесплатного отдельного поднятия нет. При полном здоровье применение недоступно и ничего не расходует.
- Сценарий выдаёт каждому герою одну повязку на самостоятельную историю. После победы повязки не восстанавливаются.
- Каждый герой может быть поднят из 0 здоровья один раз за бой. Лимит относится к спасаемому и общий для всех способов поднятия; другой помощник или предмет его не обходит. При повторном выбывании герой остаётся при 0 до конца боя и не может быть целью лечения. Пока поднятый герой на ногах, обычное последующее лечение разрешено.
- Лимит сбрасывается при начале нового столкновения; короткая пауза внутри того же боя его не обновляет. После победы здоровье каждого выжившего становится `max(текущее здоровье, 4)`, а не увеличивается на 4: выбывший возвращается с 4, герой с 1 получает 4, герой с 7 сохраняет 7.
- Интерфейс показывает запас повязок, «Поднятие доступно» / «Уже поднимали в этом бою» и предварительный результат лечения с расходом. Будущие классовые способы лечения/спасения требуют отдельного определения и соблюдают тот же лимит поднятия; параметры учебных способностей не утверждают их баланс для всей игры.

Эти правила реализованы в локальном боевом прототипе для первого игрового теста, к приключениям ещё не подключены. В демо повязка доступна себе или соседнему союзнику; выбывшие видны и занимают клетку. Классовое лечение демо остаётся доступным только героям на ногах. «Заново» полностью сбрасывает учебную сцену, включая запас повязок и лимит; переходов между боями одной истории пока нет. Проверено 29 тестов shared (25 боя), включая повторное выбывание, смену помощника, расходы, победу и поражение. Детали этапов и критериев — в `docs/combat-implementation-plan.md`.

15.11.2026 принят план внедрения медиа: единый серверный координатор связывает подтверждённые события с фонами, эмоциями, эффектами, речью и иллюстрациями; HTTP раздаёт файлы, WebSocket — статусы/команды. Провайдеры речи и картинок заменяемые: OpenAI Image API и ElevenLabs — только кандидаты, выбор сервисов и моделей может измениться. Внутри клиента связанные с речью эффекты/визуальные команды следуют позиции аудио; между клиентами — подготовка файлов, ограниченное ожидание готовности, сопоставление часов и назначенный сервером старт. Медленный/отключённый участник не удерживает группу. Готовые сцены/эффекты не ждут генератора картинки, поздние неактуальные иллюстрации идут в галерею события; переподключение не повторяет старую речь/эффекты. Первый срез: готовый архив, сцена, дверь/сундук/окружение и одна озвученная реакция на трёх клиентах с проверкой задержек/пропуска/переподключения; затем — генерация особых иллюстраций. Числа таймаутов и библиотеки плееров предварительные; детали в разделе 5.1 `docs/media-implementation-plan.md`. Реализация ещё не начата.

15.11.2026 дополнена подача историй: покадровые прологи и эпилоги с рассказчиком,
затемнением, растворением кадров и медленным движением камеры; финал содержит

## Открытые решения

15.11.2026 пользователь выбрал Qwen3-TTS для реального бесплатного теста озвучки
«Затопленного архива»: готовые фразы записываются заранее, новые реплики игроков,
NPC и рассказчика — во время партии. Тестовый вариант: 1.7B CustomVoice на серверном
ПК, faster-qwen3-tts 0.5.4 (MIT, beta), BF16/SDPA/CUDA Graphs; стандартный PyTorch
оказался слишком медленным на Windows. 22 готовых WAV и четыре образца героев —
`assets/audio/speech-qwen-v1`, игровые файлы — `shared/.../files/speech`.
Голоса фиксированы за персонажами, собственные герои получают голос класса.
Клиенты воспроизводят файлы через существующий Soundscape, новая модель на телефоны
не устанавливается. GPU-сервис доступен только на loopback:8091; сетевые клиенты
обращаются через HTTP игрового сервера. Короткие фрагменты сначала синтезируются
целиком: PCM-стриминг и общий барьер готовности пока не реализованы. Качество
русской речи и характеры оценивает пользователь. Это тест бесплатного варианта,
не решение о платном провайдере или смене текстового ИИ-ведущего.

Не считай следующие вопросы решёнными и не выбирай технологии для них без связи с текущей задачей:

- Дальнейшее развитие ИИ-гейммастера. Текущая выбранная модель — `gpt-6-luna` через OpenAI-совместимый API AI STAR (`https://ai.starimg.ru`); ключ остаётся только на сервере. Первоначальный прототип использовал `claude-sonnet-5-5` через Anthropic Messages API. Будущие смены модели требуют отдельного решения.
- Нейросети и сервисы для озвучки и генерации изображений, распределение задач между ними.
- Конкретная редакция DnD как источник дальнейших правил, развитие и подробные правила боя. Стартовые характеристики и формула проверок уже определены нашей упрощённой системой.
- Подробные правила передачи слова/боевой очереди. Состав 2–4 игрока реализован. В ИИ-режиме следующего героя выбирает ведущий, в сценарном режиме сохраняется порядок входа.
- Продукционная инфраструктура, аккаунты, постоянное хранение персонажей, сценариев и сохранений. Текущий прототип использует отдельный JVM-сервер Ktor, комнаты и приватные токены восстановления.

Выбор следующего героя до броска не адаптируется к провалу. Итоги и ограничения в README; это основания для следующей задачи, а не новые согласованные механики.

Для численных ответов добавлена серверная сводка current_facts в каждый запрос Claude: текущий/начальный запас проверок, ещё не оплаченный ожидающий бросок, каждый герой по ID/имени/месту/здоровью и все шесть реальных прямых модификаторов (отсутствующий = 0, как в движке). Она строится из снимка, не из журнала; промпт требует приоритета сводки над историей и репликой игрока, не допускает переноса бонусов между героями/характеристиками и преждевременного списания проверки. 14.11.2026 четыре отдельные реальные пробы Koog/AI STAR подтвердили исправление ложной истории (+1/+3 и остаток 2), учёт ожидающего броска, изменённые значения −2/+5 с остатком 1 и новый старт с остатком 4. Без автоматических повторов; это контрольные снимки, не повтор полного сетевого прохода. Контекст и промпт не являются формальным семантическим контролем свободной narration.

Реакция после броска и эпилог реализованы отдельным серверным OutcomeNarrator без действий/планов в ответе. Сначала движок фиксирует результат и публикует его, затем Claude дописывает только narration. Финальный бросок вызывает один эпилог вместо реакции, не оба запроса. Контекст: подтверждённые total/succeeded, герой, использованный предмет, факты и изменения состояния, точный финал, последние 24 подтверждённых механических действия и агрегированный вклад каждого за всю комнату. Диалоги и намерения не считаются эффектами; история очищается при перезапуске. Протокол 6 различает ACTION/REACTION/EPILOGUE в PendingNarration. Отмена описания, ошибка, таймаут/перегрузка не откатывают бросок; перезапуск/пропуск отключённого инвалидируют поздний ответ. Переподключение не повторяет запрос, игровых команд во время описания нет. Общие лимиты прежние, но подтверждённый бросок теперь расходует один дополнительный API-запрос. 14.11.2026 выполнено семь реальных проб на рассчитанных движком исходах; обнаружено художественное додумывание, промпт уточнён в пользу ретроспективы. Неизменность состояния защищена кодом; семантическая точность художественного текста остаётся ограничением модели. Подробнее в README.

Структура следует рекомендациям Kotlin Multiplatform: общий код и отдельные приложения с точками входа.

- `game` — KMP-модели, AdventureEngine, Kermit-диагностика, kotlinx.serialization-протокол и Ktor-клиент без зависимости от Compose.
- `server` — самостоятельный JVM-сервер Ktor CIO и WebSockets; зависит от game, не от UI.
- `shared` — общий Compose UI, ресурсы, ViewModel и сетевые экраны; зависит от game. Выпускает iOS-framework Shared.
- `androidApp` — Android-приложение, `MainActivity`, manifest и ресурсы launcher. Kotlin встроен в AGP.
- `desktopApp` — JVM-точка входа, Compose Hot Reload и упаковка приложения.
- `webApp` — Kotlin/Wasm-приложение, браузерная точка входа и HTML-оболочка. JavaScript fallback не настроен.
- `iosApp` — Xcode-проект и SwiftUI-хост; UIKit-мост находится в `shared`, framework называется `Shared`.
- `gradle/libs.versions.toml` — версии зависимостей и плагинов.
- `kotlin-js-store/wasm/yarn.lock` — lockfile зависимостей Wasm.
- `README.md` — требования к окружению и команды сборки/запуска.

Прежний модуль `composeApp` заменён на `shared` и отдельные приложения. Не используй старые Gradle-пути `:composeApp:...`.

## Сетевой прототип

- Ktor 3.6.1 (JetBrains), WebSockets `/play`, kotlinx.serialization с compiler plugin. Для KMP выбран рекомендованный Ktor `ktor-client-engine-defaults`; не настраивай неподдерживаемый OkHttp `WebSockets.maxFrameSize`.
- Сервер хранит каноническое состояние в памяти; команды и броски выполняет последовательно под Mutex. Команды содержат монотонный requestId и идентификатор хода/проверки, чтобы не повторять действия. Не доверяй ID, кубикам или игровому состоянию клиента.
- Код комнаты служит приглашением до старта. После старта разрешено только восстановление своего подключения по приватному случайному токену. Токены не попадают в публичные снимки, URL и логи.
- Клиент хранит токен только в памяти; «Подключиться снова» восстанавливает персонажа. Перезапуск приложения, обновление вкладки или явный выход теряют токен. Автоматически не повторяй игровые команды после обрыва: сначала получи снимок сервера.
- При отключении ведущего комнаты роль получает первый подключённый участник. Ведущий может убрать отключённого из лобби; после старта — пропустить только ход отключённого героя (без броска и расхода проверок). Подключённого участника пропускать нельзя.
- На клиент отправляются последние 200 записей журнала. Комнаты удаляются после 30 минут без подключений при следующем входе на сервер. Перезапуск сервера теряет все комнаты.
- Запуск: `.\gradlew.bat :server:run`, порт 8080, переопределение `DND_SERVER_PORT`. Для LAN друзья вводят адрес компьютера с сервером; для интернета нужен доступный сервер с WSS. Внешняя публикация, настройка роутера и firewall пока не выполнены.
- Android debug разрешает локальный ws://, release требует wss://. iOS содержит описание доступа к LAN и NSAllowsLocalNetworking; сборка/проверка на Windows невозможна. HTTPS-страница Wasm должна подключаться к wss://.
- Проверки: `:game:jvmTest :server:test` (включая настоящий TCP с несколькими KMP-клиентами), а также сборки Android/Desktop/Wasm. Не используй computer-use.

## Правила реализации

### Первый ИИ-ведущий

- AI STAR, Koog 1.3.0 — только в JVM-сервере. Выбранная `gpt-6-luna` использует OpenAI Chat Completions API, JSON schema и `reasoning_effort=none`; модели Claude при явном выборе используют Anthropic Messages API. Прежние имена `ANTHROPIC_API_KEY`, `DND_CLAUDE_BASE_URL` (HTTPS origin без `/v1`) и `DND_CLAUDE_MODEL` сохранены для совместимости. По умолчанию адрес `https://ai.starimg.ru`, модель `gpt-6-luna`. Без ключа работает сценарный режим. Не запрашивай ключ в чате и не включай его в исходники/логи/клиенты.
- Для локальной пробы Windows есть `scripts/start-claude-server.ps1` и исключённый из Git `server/claude.local.json` (шаблон — `server/claude.local.example.json`). Пользователь вставляет ключ сам. Не читай и не выводи заполненный локальный файл через инструменты; для диагностики используй только наличие файла и обезличенные статусы. Скрипт запускает серверный дистрибутив с ключом в окружении, без передачи ключа Gradle.
- Общий контракт двух сюжетов: Claude предлагает ID готового действия, уточнение либо SceneActionPlan с необязательной проверкой, используемым предметом и двумя ветками эффектов. Готовые действия также исполняются через SceneActionPlan. ScenarioDefinition/Scenarios/SceneRules находятся в game; места, предметы, факты, действия и финалы имеют строковые ID из выбранного определения. Инвентарь хранит ID, отображение берёт названия из каталога. Сервер валидирует обе ветки атомарно до броска и сохраняет план в PendingCheck. Эффекты: перемещение активного героя по разрешённым переходам, передача одной вещи герою рядом, описанные факты сцены с требованиями и расходом вещи, урон активному герою только при провале (суммарно до 3). Нет произвольных патчей состояния, генерации предметов/NPC, боя и долговременной памяти. Используются уже подключённые сериализация и Koog.
- ScenarioDefinition — данные, не обработчики: описания мест, предметы, начальные условия, требования (место, предмет, обязательные факты, минимум проверки, бонус от ранее установленного факта), переходы, финалы и подсказки. Не возвращай проверки сюжетных ID в общий движок или промпт. Расширяй общие эффекты только при реальной потребности нового сюжета. Публичные определения пока не содержат скрытых тайн; разделение знаний NPC ещё не реализовано.
- «Затопленный архив»: зал/двор/подвал, четыре общие проверки. Путь оригиналов — открыть дверь отмычками, спуститься, открыть сундук и защитить документы непромокаемой тканью (расходуется). Альтернатива — прочитать опись и во дворе договориться с курьером о заверенных копиях. Требования к фактам и переходам заданы в данных; новые предметы и финалы не требуют правки движка. Это второй небольшой оригинальный сценарий для проверки переносимости, не окончательная система правил.
- Политика маяка: сложность 8–18, подъём минимум 10 (8 с ранее закреплённой верёвкой). Закрепление убирает одну верёвку из inventory, эффект общий. Помощь хранителя у подножия снижает минимумы починки/сигнала с 12 до 10; не суммируется. Починка требует инструментов наверху, сигнал — фонаря; прежние действия учитывают те же условия. Любая проверка расходует одну общую попытку; безопасные планы только передают ход. Цели недоступны без проверки и допустимы только в успешной ветке. Сервер выводит подтверждённые эффекты, а не narration плана; описание намерения остаётся текстом модели. Смысловую уместность импровизации оценивают отдельно от формальной валидации.
- Протокол версии 6: виды ожидания ACTION/REACTION/EPILOGUE; выбранный текущий герой в TurnOrder и nextPlayerId в PendingCheck; публичные статус ожидания и ошибка, отмена по ID запроса владельцем; в состоянии сцена и сохранённые ветки проверки. Сервер и клиенты обновляются вместе. Ведущий выбирает известный сюжет в сетевом лобби до старта (SELECT_SCENARIO); остальные видят подтверждённый выбор. После старта менять сюжет нельзя; перезапуск сохраняет сюжет. Локальный режим предлагает выбор до начала партии и подтверждение смены сюжета. Команда подтверждается сразу; API вызывается вне Mutex. Отмена, перезапуск и пропуск отключённого героя инвалидируют ответ. Переподключение не повторяет запрос к модели. Недопустимый план не меняет журнал/ресурсы/очередь и публикует безопасную ошибку. Бросок не запрашивает план повторно: после фиксации результата запускается отдельное художественное описание без эффектов.
- Таймаут 45 секунд, до четырёх одновременных запросов без очереди и автоматических повторов, до 1600 выходных токенов (две ветки плана). В контексте определение только выбранного сюжета, последние 16 записей с ограничением длины и состояние, включая факты сцены и инвентарь. Промпт общий; JSON schema перечисляет только ID выбранного сюжета. В диагностике — только usage и статус без текстов/секретов; не включай DEBUG/TRACE Koog. Токены API не равны остатку пакета посредника с его коэффициентами.
- Тесты не требуют ключа и не расходуют токены: подставной ведущий, MockEngine клиента Koog, настоящий TCP с KMP-клиентами. 13.11.2026 реальный осмотр через AI STAR/Sonnet 5.5 успешно завершился примерно за 5,2 секунды после явного указания JSON-формата в системной инструкции. На нативный schema без инструкции не полагайся. Единственный Markdown-блок с JSON допускается со строгой проверкой содержимого; произвольный текст не преобразуется эвристиками в действие.
- 13.11.2026 отдельно подтверждены реальные свободные планы AI STAR: передача инструментов (4,3 с), закрепление верёвки (4,7 с), подъём снаружи с проверкой ловкости сложности 8 (5,3 с). Два WebSocket-клиента получили одинаковые план и итог; серверный d20=20, +3, успешное перемещение, один расход проверки. Ровно три API-запроса; ключ загружал только штатный локальный скрипт. Реальная неудачная ветка и качество полного приключения этим прогоном не проверены.
- После обобщения 14.11.2026: тесты проходят оба пути архива и регрессии маяка; настоящий TCP с двумя клиентами проверяет свободные планы архива, общие факты, переподключение перед броском и перезапуск. MockEngine проверяет новый контекст/schema через Koog без ключа.
- 14.11.2026 общий промпт проверен с реальным AI STAR для обоих сюжетов. Обнаружена и исправлена подмена нового способа ближайшим готовым действием: совпадения цели недостаточно, способ/характеристика должны соответствовать намерению; иначе нужен свободный план. После исправления прошли 7 проверок с двумя клиентами: маяк — передача инструментов, верёвка, свободный подъём STRENGTH 8 (20+1, успех); архив — опись, свободное открытие замка INTELLIGENCE 10 (2+3, провал), выход во двор, переговоры CHARISMA 12 (11+0, провал). Планы и состояния совпали, броски расходовали по одной проверке. Всего 12 API-запросов с учётом первого прогона (5+7), без автоматических повторов; штатный скрипт загрузил ключ, временный сервер остановлен. Подробности и времена в README. Это не оценка всех импровизаций и не полный реальный проход обоих сюжетов.
- Безопасная диагностика ИИ: reason, request_id, elapsed_ms; HTTP-статус и известный тип ошибки из разрешённого списка. Не сохраняй HTTP-тело, исходные exception.message/stacktrace, реплики и ключ. Usage записывается также для полученного, но отклонённого ответа. Реальная проба — подтверждение интеграции, а не качества всего сценария.

## Проверки

При использовании `imageResource` для PNG-атласов учитывай асинхронную загрузку Web: до готовности Compose возвращает прозрачную заглушку 1×1. Нельзя делить её на кадры 0×0: ContentScale получает NaN, и Painter.draw падает с `Width and height must be greater than or equal to zero`. `battleAvatarPainter` до загрузки рисует целую заглушку; после загрузки — нужный кадр. Регрессия проверяет реальный вызов отрисовки всех поз на заглушке и готовом атласе, без управления интерфейсом/скриншотов.

15.11.2026 по запросу пользователя все игровые броски сопровождаются полноэкранной анимацией в духе BG3, в янтарно-холодной палитре игры. Общий Compose-экран раскрывает подтверждённые результаты проверок характеристик, инициативы, атак (включая преимущество), урона и классового лечения. Анимация не меняет правила и не бросает кубики повторно; броски без проверки успеха не получают выдуманную сложность. Боевые DiceEvent сохраняются в журнале приключения, в том числе после окончания боя. Клиент показывает новые события по очереди, пропускает исторический снимок при входе, даёт ускорить раскрытие и автоматически продолжает; сетевой сервер не ждёт завершения анимации клиента. Реализация переносимая, без новых зависимостей; визуальную оценку выполняет пользователь.

Визуальный дизайн и поведение UI игры пользователь проверяет сам. Не используй computer-use для этого проекта: не управляй игровым интерфейсом и не выполняй визуальные проверки/снятие скриншотов вместо пользователя. Для самостоятельной проверки используй тесты, сборки и диагностические логи; это постоянное предпочтение пользователя.

Диагностика игры использует Kermit и структурированные JSONL-события с тегом DndGame. JSON формирует kotlinx.serialization (buildJsonObject); собственное экранирование строк не требуется. Схема сохраняет timestamp, event и объект fields со строковыми значениями; тесты разбирают JSON и проверяют поля. На Desktop: %LOCALAPPDATA%/dnd-game/logs/game.log (на других ОС при отсутствии LOCALAPPDATA — user.home/dnd-game/logs); каталог можно задать DND_GAME_LOG_DIR или JVM-свойством dnd.game.logDir. Ротацию выполняет kermit-io: два файла примерно по 5 МиБ. На Android ищи тег DndGame в Logcat, на iOS — в системных/Xcode-логах, на Wasm — в консоли браузера. Проверяй логи программно, без computer-use. Не добавляй в диагностические логи полный текст реплик, промптов, ответы ИИ или секреты. Логи отделены от игрового журнала; ошибка логгера не должна менять исход действия.

Для изменения только документации достаточно проверить содержание, ссылки/пути и diff; полная сборка не нужна.

После изменений кода выполняй проверки затронутых платформ. Для изменений общей конфигурации или зависимостей проверяй доступные на текущем хосте платформы:

```powershell
.\gradlew.bat :desktopApp:classes :webApp:wasmJsBrowserDistribution :androidApp:assembleDebug
```

На macOS/Linux используй `./gradlew`. Сборка iOS выполняется через `iosApp/iosApp.xcodeproj`; Xcode вызывает `:shared:embedAndSignAppleFrameworkForXcode`. Не сообщай об успешной проверке iOS по результатам сборки на Windows.

Добавляй содержательные тесты для игровых правил, изменения состояния и исправлений ошибок. Не создавай формальные тесты, дублирующие реализацию простых UI/документационных правок. Команды тестов выбирай по фактически настроенным source sets.

На момент создания файла успешно проверены Android debug APK, компиляция Desktop и production-дистрибутив Wasm. Это исторический результат, а не замена проверке последующих изменений. Запуск Desktop и отображение нового экрана проверены. iOS и запуск на Android-устройстве отдельно не проверены.
