# AGENTS.md

## Назначение и контекст

Этот файл содержит постоянный контекст и правила для агентов, работающих с репозиторием `dnd-game`. Читай его при начале новой сессии вместе с `README.md` и конфигурацией затрагиваемых модулей. Актуальное состояние реализации проверяй по исходникам и Git diff.

Обновляй этот файл, когда пользователь принимает значимые решения о продукте, архитектуре или процессе работы. Сохраняй причины важных решений кратко; не превращай файл в журнал переписки. Пользовательские указания текущей сессии имеют приоритет.

## Концепция игры: согласованное направление

Мультиплатформенная ролевая игра в стиле DnD, в которой роль гейммастера выполняет нейронная сеть.

- Игроки выбирают сценарии и проходят их как отдельные сюжеты.
- Игрок может создать нового или выбрать существующего персонажа с характеристиками в духе DnD.
- Игроки сообщают гейммастеру действия своего персонажа. На начальном этапе ввод действий — текстовый.
- Для игровых проверок используются броски кубиков.
- Боевая система предполагается пошаговой, в духе DnD; точные правила будут определены позже.
- Отдельная нейросеть или несколько нейросетей будут озвучивать текст игроков и гейммастера.
- Генерация изображений будет визуализировать происходящие события на экране.

Это направление разработки, а не перечень уже реализованных возможностей.

## Открытые решения

Не считай следующие вопросы решёнными и не выбирай технологии для них без связи с текущей задачей:

- Модель, провайдер, протокол и способ интеграции ИИ-гейммастера.
- Нейросети и сервисы для озвучки и генерации изображений, распределение задач между ними.
- Конкретная редакция DnD, набор характеристик, формулы проверок и подробные правила боя.
- Режимы игры, количество игроков, сетевой мультиплеер и синхронизация.
- Серверная архитектура, авторизация, хранение персонажей, сценариев и сохранений.
- Источник и формат сценариев, управление контекстом сюжета и памятью гейммастера.
- Голосовой ввод: пока согласован только текстовый ввод действий.

Не подменяй открытые вопросы собственной окончательной спецификацией. Если задача требует решения, обозначь допущение или уточни существенный выбор. Для работы над независимыми частями продолжай с имеющимися данными.

## Текущее состояние и модули

Проект находится на стадии стартового KMP/Compose-шаблона с демонстрационным экраном. Игровые механики и интеграции ИИ пока не реализованы.

Структура следует рекомендациям Kotlin Multiplatform: общий код и отдельные приложения с точками входа.

- `shared` — общий Compose UI, ресурсы и логика в `commonMain`; платформенные реализации в `androidMain`, `iosMain`, `jvmMain`, `wasmJsMain`.
- `androidApp` — Android-приложение, `MainActivity`, manifest и ресурсы launcher. Kotlin встроен в AGP.
- `desktopApp` — JVM-точка входа, Compose Hot Reload и упаковка приложения.
- `webApp` — Kotlin/Wasm-приложение, браузерная точка входа и HTML-оболочка. JavaScript fallback не настроен.
- `iosApp` — Xcode-проект и SwiftUI-хост; UIKit-мост находится в `shared`, framework называется `Shared`.
- `gradle/libs.versions.toml` — версии зависимостей и плагинов.
- `kotlin-js-store/wasm/yarn.lock` — lockfile зависимостей Wasm.
- `README.md` — требования к окружению и команды сборки/запуска.

Прежний модуль `composeApp` заменён на `shared` и отдельные приложения. Не используй старые Gradle-пути `:composeApp:...`.

## Правила реализации

- Общую игровую логику и переносимый UI размещай в `shared/commonMain`; код конкретной платформы — в соответствующем source set или модуле приложения.
- Сохраняй совместимость Android, iOS, Desktop и Wasm. Не добавляй JVM/Android API и несовместимые зависимости в общий код.
- Разделяй игровое состояние, проверки и броски кубиков, UI и обращения к внешним ИИ-сервисам. Конкретные абстракции вводи по мере появления задач, без преждевременного дробления на модули.
- При реализации случайных проверок обеспечивай возможность подменить источник случайности для воспроизводимых тестов.
- Вызовы генерации текста, озвучки и изображений выполняй асинхронно; предусматривай состояние ожидания, ошибку и возможность отмены.
- Не добавляй реальные секреты в исходники, ресурсы, логи или Git. Для будущих сервисов способ хранения ключей определяется отдельно; не встраивай секретные ключи в распространяемые клиенты.
- Изменения делай в рамках задачи. Не перезаписывай пользовательские правки, не меняй Git index, не коммить и не публикуй без соответствующего запроса.
- Сохраняй стандартные префиксы коммитов (`feat:`, `fix:`, `docs:`, `refactor:` и другие), а текст заголовка после префикса и описание пиши на русском языке. Это постоянное предпочтение пользователя.
- Объясняй результат по-русски: что изменилось, что проверено и какие ограничения остались.

## Зависимости и окружение

Перед обновлением проверяй актуальную официальную документацию KMP и совместимость Kotlin, Compose, AGP и Gradle. Не обновляй каждый компонент независимо до максимальной версии.

Точные версии бери из version catalog и Gradle wrapper. На момент создания файла: Kotlin 2.4.21, Compose Multiplatform 1.12.2, AGP 9.3.1, Gradle 9.7.0. Material3 использует отдельную alpha-версию; это отражено в README.

- JDK 21 для Gradle и Desktop/Hot Reload.
- Android: compile SDK 37, target SDK 36, min SDK 24. При изменениях сверяйся с version catalog.
- iOS: macOS и Xcode; ориентир совместимости текущей связки — Xcode 26.4.
- Web: браузер с поддержкой WasmGC.
- Используй Gradle wrapper. Не закрепляй в проекте абсолютные пути к локальным JDK/SDK пользователя.

## Проверки

Для изменения только документации достаточно проверить содержание, ссылки/пути и diff; полная сборка не нужна.

После изменений кода выполняй проверки затронутых платформ. Для изменений общей конфигурации или зависимостей проверяй доступные на текущем хосте платформы:

```powershell
.\gradlew.bat :desktopApp:classes :webApp:wasmJsBrowserDistribution :androidApp:assembleDebug
```

На macOS/Linux используй `./gradlew`. Сборка iOS выполняется через `iosApp/iosApp.xcodeproj`; Xcode вызывает `:shared:embedAndSignAppleFrameworkForXcode`. Не сообщай об успешной проверке iOS по результатам сборки на Windows.

Добавляй содержательные тесты для игровых правил, изменения состояния и исправлений ошибок. Не создавай формальные тесты, дублирующие реализацию простых UI/документационных правок. Команды тестов выбирай по фактически настроенным source sets.

На момент создания файла успешно проверены Android debug APK, компиляция Desktop и production-дистрибутив Wasm. Это исторический результат, а не замена проверке последующих изменений. Запуск приложений и iOS отдельно не проверены.
