# AGENTS.md

## Назначение и контекст

Этот файл содержит постоянный контекст и правила для агентов, работающих с репозиторием `dnd-game`. Читай его при начале новой сессии вместе с `README.md` и конфигурацией затрагиваемых модулей. Актуальное состояние реализации проверяй по исходникам и Git diff.

Обновляй этот файл, когда пользователь принимает значимые решения о продукте, архитектуре или процессе работы. Сохраняй причины важных решений кратко; не превращай файл в журнал переписки. Пользовательские указания текущей сессии имеют приоритет.

## Концепция игры: согласованное направление

Мультиплатформенная ролевая игра в стиле DnD, в которой роль гейммастера выполняет нейронная сеть.

Используем упрощённые правила по впечатлению от «Подземелий Чикен Карри». Полная реализация DnD не является целью; точные формулы, набор характеристик и детали боя ещё не выбраны. Сходство с шоу — ориентир, а не утверждение о его точных механиках.

- Основной формат игры — совместное прохождение с друзьями по сети. Сетевой мультиплеер является согласованной целью проекта.
- Игроки выполняют действия по очереди в ходе приключения, а не только во время боя. Конкретный порядок и правила передачи хода будут определены позже.
- Игроки выбирают сценарии и проходят их как отдельные сюжеты.
- Игрок может создать нового или выбрать существующего персонажа с характеристиками в духе DnD.
- Игроки сообщают гейммастеру действия своего персонажа. На начальном этапе ввод действий — текстовый.
- Для игровых проверок используются броски кубиков.
- Боевая система предполагается пошаговой, в духе DnD; точные правила будут определены позже.
- Отдельная нейросеть или несколько нейросетей будут озвучивать текст игроков и гейммастера.
- Генерация изображений будет визуализировать происходящие события на экране.

Это направление разработки, а не перечень уже реализованных возможностей.

## Открытые решения

Не считай следующие вопросы решёнными и не выбирай технологии для них без связи с текущей задачей:

- Конкретная модель и дальнейшее развитие ИИ-гейммастера. Для первого прототипа выбран Claude через AI STAR (`https://ai.starimg.ru`), Anthropic Messages API; ключ хранится в окружении удалённого сервера. Модель настраивается сервером, первоначальное значение — `claude-sonnet-5-5`; доступность по ключу требует живой проверки.
- Нейросети и сервисы для озвучки и генерации изображений, распределение задач между ними.
- Конкретная редакция DnD, набор характеристик, формулы проверок и подробные правила боя.
- Окончательное количество игроков и правила очереди. Для первого сетевого прототипа выбраны комнаты на 2–3 участников и фиксированная очередь входа.
- Продукционная инфраструктура, аккаунты, постоянное хранение персонажей, сценариев и сохранений. Текущий прототип использует отдельный JVM-сервер Ktor, комнаты и приватные токены восстановления.
- Источник и внешний формат сценариев, управление контекстом сюжета и памятью гейммастера. Для двух прототипов используются встроенные сериализуемые Kotlin-определения ScenarioDefinition; внешнего загрузчика и редактора нет.
- Голосовой ввод: пока согласован только текстовый ввод действий.

Не подменяй открытые вопросы собственной окончательной спецификацией. Если задача требует решения, обозначь допущение или уточни существенный выбор. Для работы над независимыми частями продолжай с имеющимися данными.

## Текущее состояние и модули

Реализованы локальный и сетевой прототипы приключений «Погасший маяк» и «Затопленный архив»: состояние героев, журнал, текстовые действия, проверки d20, альтернативные финалы. Общий Compose UI находится в shared, состояние/правила/диагностика и протокол — в game. AdventureEngine выполняет единые планы готовых и свободных действий. Условия сюжетов заданы данными ScenarioDefinition в Scenarios.kt; SceneRules не содержит ветвлений по сюжетным ID. Локально доступны три готовых участника на одном устройстве со сценарным ведущим. Сетевые комнаты рассчитаны на 2–3 друзей с отдельными клиентами; герои назначаются по порядку входа. Создатель запускает игру, каждый управляет только своим персонажем. Сетевой сервер опционально подключает Claude через AI STAR для диалогов, осмотра и предложений новых способов действий в пределах выбранного сюжета. Последствия проверяет и применяет сервер; постоянные сохранения и бой ещё не реализованы.

Предварительные правила локального прототипа: d20 + прямой модификатор против сложности, равенство — успех, без особого эффекта 1/20; запас проверок задаёт сценарий: три до прибытия парома или четыре до затопления архива. Завершённое действие передаёт ход следующему участнику; действие с проверкой завершается после броска. Осмотр/разговор передают ход, но не расходуют запас проверок. Отмена до броска, неподдержанный текст и недоступное действие сохраняют ход. Кнопка «Передать ход» пропускает очередь без расхода проверок. Команды содержат ID игрока и идентификатор текущего хода; запросы броска закреплены за владельцем, запоздавшие и повторные команды отклоняются. Локальный режим проверяет ID; в сети сервер определяет ID по подключению и сам выполняет правила и броски. Это настройки двух демонстрационных сценариев, а не окончательные правила игры. Модели и обработчик находятся в game/src/commonMain/kotlin/ru/markn/dnd/adventure, UI — в shared/src/commonMain/kotlin/ru/markn/dnd/adventure/ui, тесты логики — в game/src/commonTest.

Структура следует рекомендациям Kotlin Multiplatform: общий код и отдельные приложения с точками входа.

- `game` — KMP-модели, AdventureEngine, Kermit-диагностика, kotlinx.serialization-протокол и Ktor-клиент без зависимости от Compose.
- `server` — самостоятельный JVM-сервер Ktor CIO и WebSockets; зависит от game, не от UI.
- `shared` — общий Compose UI, ресурсы, ViewModel и сетевые экраны; зависит от game. Выпускает iOS-framework Shared.
- `androidApp` — Android-приложение, `MainActivity`, manifest и ресурсы launcher. Kotlin встроен в AGP.
- `desktopApp` — JVM-точка входа, Compose Hot Reload и упаковка приложения.
- `webApp` — Kotlin/Wasm-приложение, браузерная точка входа и HTML-оболочка. JavaScript fallback не настроен.
- `iosApp` — Xcode-проект и SwiftUI-хост; UIKit-мост находится в `shared`, framework называется `Shared`.
- `gradle/libs.versions.toml` — версии зависимостей и плагинов.
- `kotlin-js-store/wasm/yarn.lock` — lockfile зависимостей Wasm.
- `README.md` — требования к окружению и команды сборки/запуска.

Прежний модуль `composeApp` заменён на `shared` и отдельные приложения. Не используй старые Gradle-пути `:composeApp:...`.

## Сетевой прототип

- Ktor 3.6.1 (JetBrains), WebSockets `/play`, kotlinx.serialization с compiler plugin. Для KMP выбран рекомендованный Ktor `ktor-client-engine-defaults`; не настраивай неподдерживаемый OkHttp `WebSockets.maxFrameSize`.
- Сервер хранит каноническое состояние в памяти; команды и броски выполняет последовательно под Mutex. Команды содержат монотонный requestId и идентификатор хода/проверки, чтобы не повторять действия. Не доверяй ID, кубикам или игровому состоянию клиента.
- Код комнаты служит приглашением до старта. После старта разрешено только восстановление своего подключения по приватному случайному токену. Токены не попадают в публичные снимки, URL и логи.
- Клиент хранит токен только в памяти; «Подключиться снова» восстанавливает персонажа. Перезапуск приложения, обновление вкладки или явный выход теряют токен. Автоматически не повторяй игровые команды после обрыва: сначала получи снимок сервера.
- При отключении ведущего комнаты роль получает первый подключённый участник. Ведущий может убрать отключённого из лобби; после старта — пропустить только ход отключённого героя (без броска и расхода проверок). Подключённого участника пропускать нельзя.
- На клиент отправляются последние 200 записей журнала. Комнаты удаляются после 30 минут без подключений при следующем входе на сервер. Перезапуск сервера теряет все комнаты.
- Запуск: `.\gradlew.bat :server:run`, порт 8080, переопределение `DND_SERVER_PORT`. Для LAN друзья вводят адрес компьютера с сервером; для интернета нужен доступный сервер с WSS. Внешняя публикация, настройка роутера и firewall пока не выполнены.
- Android debug разрешает локальный ws://, release требует wss://. iOS содержит описание доступа к LAN и NSAllowsLocalNetworking; сборка/проверка на Windows невозможна. HTTPS-страница Wasm должна подключаться к wss://.
- Проверки: `:game:jvmTest :server:test` (включая настоящий TCP с несколькими KMP-клиентами), а также сборки Android/Desktop/Wasm. Не используй computer-use.

## Правила реализации

### Первый ИИ-ведущий

- Claude через AI STAR, Anthropic Messages API; Koog 1.3.0 — только в JVM-сервере. `ANTHROPIC_API_KEY`, `DND_CLAUDE_BASE_URL` (HTTPS origin без `/v1`) и `DND_CLAUDE_MODEL` задаются в окружении сервера. По умолчанию адрес `https://ai.starimg.ru`, модель `claude-sonnet-5-5`. Без ключа работает сценарный режим. Не запрашивай ключ в чате и не включай его в исходники/логи/клиенты.
- Для локальной пробы Windows есть `scripts/start-claude-server.ps1` и исключённый из Git `server/claude.local.json` (шаблон — `server/claude.local.example.json`). Пользователь вставляет ключ сам. Не читай и не выводи заполненный локальный файл через инструменты; для диагностики используй только наличие файла и обезличенные статусы. Скрипт запускает серверный дистрибутив с ключом в окружении, без передачи ключа Gradle.
- Общий контракт двух сюжетов: Claude предлагает ID готового действия, уточнение либо SceneActionPlan с необязательной проверкой, используемым предметом и двумя ветками эффектов. Готовые действия также исполняются через SceneActionPlan. ScenarioDefinition/Scenarios/SceneRules находятся в game; места, предметы, факты, действия и финалы имеют строковые ID из выбранного определения. Инвентарь хранит ID, отображение берёт названия из каталога. Сервер валидирует обе ветки атомарно до броска и сохраняет план в PendingCheck. Эффекты: перемещение активного героя по разрешённым переходам, передача одной вещи герою рядом, описанные факты сцены с требованиями и расходом вещи, урон активному герою только при провале (суммарно до 3). Нет произвольных патчей состояния, генерации предметов/NPC, боя и долговременной памяти. Используются уже подключённые сериализация и Koog.
- ScenarioDefinition — данные, не обработчики: описания мест, предметы, начальные условия, требования (место, предмет, обязательные факты, минимум проверки, бонус от ранее установленного факта), переходы, финалы и подсказки. Не возвращай проверки сюжетных ID в общий движок или промпт. Расширяй общие эффекты только при реальной потребности нового сюжета. Публичные определения пока не содержат скрытых тайн; разделение знаний NPC ещё не реализовано.
- «Затопленный архив»: зал/двор/подвал, четыре общие проверки. Путь оригиналов — открыть дверь отмычками, спуститься, открыть сундук и защитить документы непромокаемой тканью (расходуется). Альтернатива — прочитать опись и во дворе договориться с курьером о заверенных копиях. Требования к фактам и переходам заданы в данных; новые предметы и финалы не требуют правки движка. Это второй небольшой оригинальный сценарий для проверки переносимости, не окончательная система правил.
- Политика маяка: сложность 8–18, подъём минимум 10 (8 с ранее закреплённой верёвкой). Закрепление убирает одну верёвку из inventory, эффект общий. Помощь хранителя у подножия снижает минимумы починки/сигнала с 12 до 10; не суммируется. Починка требует инструментов наверху, сигнал — фонаря; прежние действия учитывают те же условия. Любая проверка расходует одну общую попытку; безопасные планы только передают ход. Цели недоступны без проверки и допустимы только в успешной ветке. Сервер выводит подтверждённые эффекты, а не narration плана; описание намерения остаётся текстом модели. Смысловую уместность импровизации оценивают отдельно от формальной валидации.
- Протокол версии 4: публичные статус ожидания и ошибка, отмена по ID запроса владельцем; в состоянии сцена и сохранённые ветки проверки. Сервер и клиенты обновляются вместе. Ведущий выбирает известный сюжет в сетевом лобби до старта (SELECT_SCENARIO); остальные видят подтверждённый выбор. После старта менять сюжет нельзя; перезапуск сохраняет сюжет. Локальный режим предлагает выбор до начала партии и подтверждение смены сюжета. Команда подтверждается сразу; API вызывается вне Mutex. Отмена, перезапуск и пропуск отключённого героя инвалидируют ответ. Переподключение не повторяет запрос к модели. Недопустимый план не меняет журнал/ресурсы/очередь и публикует безопасную ошибку. Бросок не вызывает модель повторно.
- Таймаут 45 секунд, до четырёх одновременных запросов без очереди и автоматических повторов, до 1600 выходных токенов (две ветки плана). В контексте определение только выбранного сюжета, последние 16 записей с ограничением длины и состояние, включая факты сцены и инвентарь. Промпт общий; JSON schema перечисляет только ID выбранного сюжета. В диагностике — только usage и статус без текстов/секретов; не включай DEBUG/TRACE Koog. Токены API не равны остатку пакета посредника с его коэффициентами.
- Тесты не требуют ключа и не расходуют токены: подставной ведущий, MockEngine клиента Koog, настоящий TCP с KMP-клиентами. 13.11.2026 реальный осмотр через AI STAR/Sonnet 5.5 успешно завершился примерно за 5,2 секунды после явного указания JSON-формата в системной инструкции. На нативный schema без инструкции не полагайся. Единственный Markdown-блок с JSON допускается со строгой проверкой содержимого; произвольный текст не преобразуется эвристиками в действие.
- 13.11.2026 отдельно подтверждены реальные свободные планы AI STAR: передача инструментов (4,3 с), закрепление верёвки (4,7 с), подъём снаружи с проверкой ловкости сложности 8 (5,3 с). Два WebSocket-клиента получили одинаковые план и итог; серверный d20=20, +3, успешное перемещение, один расход проверки. Ровно три API-запроса; ключ загружал только штатный локальный скрипт. Реальная неудачная ветка и качество полного приключения этим прогоном не проверены.
- После обобщения 14.11.2026: тесты проходят оба пути архива и регрессии маяка; настоящий TCP с двумя клиентами проверяет свободные планы архива, общие факты, переподключение перед броском и перезапуск. MockEngine проверяет новый контекст/schema через Koog без ключа.
- 14.11.2026 общий промпт проверен с реальным AI STAR для обоих сюжетов. Обнаружена и исправлена подмена нового способа ближайшим готовым действием: совпадения цели недостаточно, способ/характеристика должны соответствовать намерению; иначе нужен свободный план. После исправления прошли 7 проверок с двумя клиентами: маяк — передача инструментов, верёвка, свободный подъём STRENGTH 8 (20+1, успех); архив — опись, свободное открытие замка INTELLIGENCE 10 (2+3, провал), выход во двор, переговоры CHARISMA 12 (11+0, провал). Планы и состояния совпали, броски расходовали по одной проверке. Всего 12 API-запросов с учётом первого прогона (5+7), без автоматических повторов; штатный скрипт загрузил ключ, временный сервер остановлен. Подробности и времена в README. Это не оценка всех импровизаций и не полный реальный проход обоих сюжетов.
- Безопасная диагностика ИИ: reason, request_id, elapsed_ms; HTTP-статус и известный тип ошибки из разрешённого списка. Не сохраняй HTTP-тело, исходные exception.message/stacktrace, реплики и ключ. Usage записывается также для полученного, но отклонённого ответа. Реальная проба — подтверждение интеграции, а не качества всего сценария.

### Размещение и изменения кода

- Общие модели, правила, диагностику и сетевой протокол размещай в `game/src/commonMain`; переносимый UI и ViewModel — в `shared/src/commonMain`; сервер — в `server`. Код конкретной платформы — в соответствующем source set.
- Сохраняй совместимость Android, iOS, Desktop и Wasm. Не добавляй JVM/Android API и несовместимые зависимости в общий код.
- Разделяй игровое состояние, проверки и броски кубиков, UI и обращения к внешним ИИ-сервисам. Конкретные абстракции вводи по мере появления задач, без преждевременного дробления на модули.
- При реализации случайных проверок обеспечивай возможность подменить источник случайности для воспроизводимых тестов.
- Вызовы генерации текста, озвучки и изображений выполняй асинхронно; предусматривай состояние ожидания, ошибку и возможность отмены.
- Не добавляй реальные секреты в исходники, ресурсы, логи или Git. Для будущих сервисов способ хранения ключей определяется отдельно; не встраивай секретные ключи в распространяемые клиенты.
- Изменения делай в рамках задачи. Не перезаписывай пользовательские правки, не меняй Git index, не коммить и не публикуй без соответствующего запроса.
- Сохраняй стандартные префиксы коммитов (`feat:`, `fix:`, `docs:`, `refactor:` и другие), а текст заголовка после префикса и описание пиши на русском языке. Это постоянное предпочтение пользователя.
- Объясняй результат по-русски: что изменилось, что проверено и какие ограничения остались.

## Зависимости и окружение

Постоянное предпочтение пользователя по реализации технической части:

- Прежде чем писать собственную инфраструктуру или техническую утилиту, проверь, решается ли задача готовой современной, поддерживаемой и актуальной KMP-библиотекой. При подходящем готовом решении предпочитай его реализации с нуля.
- В первую очередь рассматривай библиотеки Kotlin/JetBrains, затем решения, которые они рекомендуют в официальной документации. Если подходящего варианта нет, выбирай поддерживаемую стороннюю библиотеку с учётом задачи.
- Перед подключением и использованием новой библиотеки предупреди пользователя: назови библиотеку, её назначение и кратко объясни выбор. Это предварительное уведомление, а не обязательный запрос отдельного подтверждения.
- Актуальность, рекомендации и поддержку нужных платформ проверяй по первичным источникам; для общего кода учитывай Android, iOS, JVM и Wasm. Предпочитай стабильные совместимые версии; предварительную версию и причину её выбора указывай явно.
- Не вводи зависимость только ради её наличия. Если готовое решение не подходит, кратко объясни причину и реализуй необходимый объём собственного кода. Игровые правила и логику сценариев определяй по требованиям проекта.

Перед обновлением проверяй актуальную официальную документацию KMP и совместимость Kotlin, Compose, AGP и Gradle. Не обновляй каждый компонент независимо до максимальной версии.

Точные версии бери из version catalog и Gradle wrapper. На момент создания файла: Kotlin 2.4.21, Compose Multiplatform 1.12.2, AGP 9.3.1, Gradle 9.7.0. Material3 использует отдельную alpha-версию; это отражено в README.

- JDK 21 для Gradle и Desktop/Hot Reload.
- Android: compile SDK 37, target SDK 36, min SDK 24. При изменениях сверяйся с version catalog.
- iOS: macOS и Xcode; ориентир совместимости текущей связки — Xcode 26.4.
- Web: браузер с поддержкой WasmGC.
- Используй Gradle wrapper. Не закрепляй в проекте абсолютные пути к локальным JDK/SDK пользователя.

## Проверки

Визуальный дизайн и поведение UI игры пользователь проверяет сам. Не используй computer-use для этого проекта: не управляй игровым интерфейсом и не выполняй визуальные проверки/снятие скриншотов вместо пользователя. Для самостоятельной проверки используй тесты, сборки и диагностические логи; это постоянное предпочтение пользователя.

Диагностика игры использует Kermit и структурированные JSONL-события с тегом DndGame. JSON формирует kotlinx.serialization (buildJsonObject); собственное экранирование строк не требуется. Схема сохраняет timestamp, event и объект fields со строковыми значениями; тесты разбирают JSON и проверяют поля. На Desktop: %LOCALAPPDATA%/dnd-game/logs/game.log (на других ОС при отсутствии LOCALAPPDATA — user.home/dnd-game/logs); каталог можно задать DND_GAME_LOG_DIR или JVM-свойством dnd.game.logDir. Ротацию выполняет kermit-io: два файла примерно по 5 МиБ. На Android ищи тег DndGame в Logcat, на iOS — в системных/Xcode-логах, на Wasm — в консоли браузера. Проверяй логи программно, без computer-use. Не добавляй в диагностические логи полный текст реплик, промптов, ответы ИИ или секреты. Логи отделены от игрового журнала; ошибка логгера не должна менять исход действия.

Для изменения только документации достаточно проверить содержание, ссылки/пути и diff; полная сборка не нужна.

После изменений кода выполняй проверки затронутых платформ. Для изменений общей конфигурации или зависимостей проверяй доступные на текущем хосте платформы:

```powershell
.\gradlew.bat :desktopApp:classes :webApp:wasmJsBrowserDistribution :androidApp:assembleDebug
```

На macOS/Linux используй `./gradlew`. Сборка iOS выполняется через `iosApp/iosApp.xcodeproj`; Xcode вызывает `:shared:embedAndSignAppleFrameworkForXcode`. Не сообщай об успешной проверке iOS по результатам сборки на Windows.

Добавляй содержательные тесты для игровых правил, изменения состояния и исправлений ошибок. Не создавай формальные тесты, дублирующие реализацию простых UI/документационных правок. Команды тестов выбирай по фактически настроенным source sets.

На момент создания файла успешно проверены Android debug APK, компиляция Desktop и production-дистрибутив Wasm. Это исторический результат, а не замена проверке последующих изменений. Запуск Desktop и отображение нового экрана проверены. iOS и запуск на Android-устройстве отдельно не проверены.
